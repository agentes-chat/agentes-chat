# 0174. The Copilot brain: agents think with a person's GitHub Copilot plan through the Copilot CLI

- Status: Accepted (2026-11-12; built: runner, engine, server, the shared client, the web and the phone app). The flags, files and events in §2–§5 are read from `copilot --help` and `copilot help` and run against Copilot CLI 1.0.109: the runner's turn (`handleCopilotBrainTurn`, called directly on Windows 11) with a tool of its own, a call to an MCP server, a resume, a `plan` turn's denied write and an MCP server that fails to start, on a computer signed in through `gh`; and signed out on Linux (a turn, a session, a refused token, the device code's words). Not yet run: a sign-in kept in an account's folder, a turn through a paired computer and the apps' screens; the probes in §8 come before it ships.
- Date: 2026-11-12
- Extends: ADR 0032 (computer brains), ADR 0041 (accounts per agent), ADR 0053 §3 (permission profiles), ADR 0059 (AI accounts belong to people), ADR 0117 (injection hardening), ADR 0132 (the OpenCode brain, whose missing sandbox this shares), ADR 0142 (the Grok brain, whose shape this mirrors)

## Context

GitHub ships the Copilot CLI (`copilot`), included in every paid GitHub Copilot plan. It signs in with the person's GitHub account by browser or by a device code, runs without a terminal when a prompt is given, and prints its own JSONL (`--output-format json`). One plan reaches models of several makers (Anthropic's, OpenAI's, Google's, xAI's and others), each counted against the plan at its own rate. This adds GitHub Copilot plans next to Claude's, ChatGPT's, Cursor's, OpenCode's, Grok's and Gemini's.

What the CLI does, read in `copilot --help`, `copilot login --help` and `copilot help config|environment|mcp|permissions|sessions|sandbox|limits|acp`, and run on 1.0.109 (2026-11-12):

- Everything lives in `COPILOT_HOME` (default `~/.copilot`): `settings.json` (the person's settings), `config.json` (what the CLI manages: trusted folders, the sign-in), `mcp-config.json`, `copilot-instructions.md`, `instructions/`, `agents/`, `skills/`, `hooks/`, `installed-plugins/`, `permissions-config.json`, `providers.json`, `session-state/<id>/` (one folder per session) and `logs/`. Personal skills are also read from `~/.agents/skills`, which `ignoredSkillsLocations` leaves out.
- Sign-in: `copilot login --device-code` prints "To authenticate, visit https://github.com/login/device and enter code XXXX-XXXX" and waits. The token goes to the OS credential store, or with `storeTokenPlaintext` to a file under `COPILOT_HOME`. There is no sign-out command and no status command. Signed out, a turn prints "No authentication information found." on standard error and exits 1; a token GitHub refuses, "Authentication token found but could not be validated … Bad credentials".
- Who it thinks as, in order: `COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`, the stored sign-in, then the GitHub CLI's own sign-in (`gh auth login`).
- A turn: the message on standard input (or `-p <text>`), `--output-format json`, `--model`, `--reasoning-effort`, `--resume=<id>`. Its events: `session.start` (`sessionId`) or `session.resume`, `assistant.message_delta` (`deltaContent`), `assistant.message` (`content`, `toolRequests`), `tool.execution_start` and `tool.execution_complete` (`toolCallId`, `toolName`, `mcpServerName` for an MCP server's, `success`, `result.content`), `session.error` (`message`), `session.usage_checkpoint` (tokens per model, counted over the whole session) and a last `result` (`sessionId`, `exitCode`). A `--resume` of a session it doesn't have exits 1 with "No session, task, or name matched".
- MCP servers for one run: `--additional-mcp-config @file` (`mcpServers.<name>`, `type: "local"` with `command` and `args`, or `"http"` with `url` and `headers`). A local server inherits the CLI's environment; its tools are named `<server>-<tool>`. `--disable-builtin-mcps` turns GitHub's own off.
- Permissions: with no terminal, a tool request no rule allows is denied. `--allow-all-tools`, `--allow-tool <kind>` (`read`, `write`, `shell(...)`, `<mcp-server>`), `--deny-tool` (which wins), `--allow-all-urls`. File access stays in the working directory and the temp directory unless `--allow-all-paths`. A run in a folder nobody trusted skips its MCP servers and hooks; `COPILOT_ALLOW_ALL=true` trusts it.
- Its command sandbox (`copilot help sandbox`) is off by default and needs bubblewrap, slirp4netns and more on Linux; where it can't run, every command fails.
- No `models` command. Its Agent Client Protocol server (`copilot --acp --stdio`) lists them when a session opens (`session/new`: `models.availableModels`), or answers "Authentication required" (-32000) signed out, with no prompt and nothing counted against the plan.
- `--no-custom-instructions` (no `AGENTS.md` and the like), `--no-auto-update`, `--no-ask-user`, `--sync-session=off` (session history is otherwise sent to the person's GitHub account), and the settings `autoUpdate`, `remoteExport`, `memory`, `disableAllHooks`.

## Decision

1. **An eighth computer brain** (`BrainKind` and `AccountKind` `copilot`, `BRAIN_NAMES` "Copilot CLI", `BRAIN_PLAN_NAMES` "GitHub Copilot", plan choice `copilot`), the same `brain.turn` as Codex, Cursor and Grok (`CopilotBrain` in `brains/codex.ts`, `COPILOT_CLI`). Runner protocol 65 (`COPILOT_PROTOCOL`): `brain.turn` `kind: "copilot"`, `account` `kind: "copilot"`, `hello.executors.copilot` (the version line), `access.tools.copilot` (absent: follows Codex's, like Cursor's and OpenCode's). Missing CLI: `copilot_missing`. No live steering: `brain.steer` answers `unsupported`. Usage is the person's plan (tokens recorded, cost zero), limits and sign-in failures by the CLI's words (`plan_limit`, `not_logged_in`).
2. **One `copilot` per turn** (`brain-copilot.ts`): `--output-format json --no-custom-instructions --disable-builtin-mcps --no-auto-update --no-ask-user --sync-session=off --additional-mcp-config @<file>`, with `--model`, `--reasoning-effort` (`xhigh` and `max` as `high`) and `--resume=<id>` for a chat it knows. The message goes on standard input, so no context is cut to fit a command line and none shows in the process list. Its events are mapped by `CopilotEventMapper`: text from the deltas, or whole from `assistant.message` when none came, each message a paragraph apart; a tool of its own as a `tool_call` with what it answered; our bridge's calls (`mcpServerName` ours) left out, since the engine ran them; the answer is the text after the last tool. Our session → Copilot's session is kept per account in `copilot-chats.json`, beside what the session had used when the turn ended: the CLI counts usage over the whole session, so a turn's is the difference. A new chat leads its message with the engine's context, and a resume the CLI can't find starts a new chat once. The chat is kept only when a turn ends with the assistant having said or called something: one that was canceled, lost our bridge or never spoke leaves none, so the next turn starts it again with the context. A run that ends well with no words and no call is `copilot_failed`, never an empty answer. Our MCP server failing to start (`session.mcp_server_status_changed`, `failed`) ends the turn at once: the CLI would otherwise answer with its own tools alone.
3. **Always an account.** `COPILOT_HOME` is the account's folder. Before every turn and before the sign-in the runner writes its `settings.json` whole (`COPILOT_SETTINGS`: `storeTokenPlaintext`, so two accounts never share the OS credential store's one sign-in; no self-update, no session history sent to GitHub, no memory, no hooks, none of the computer user's personal skills) and removes what a turn could have planted for a later one (`COPILOT_PLANTED`: MCP servers, instructions, agents, skills, hooks, plugins, extensions, prompts, saved approvals, another model provider). Our MCP server alone goes in a file there: stdio (`agentes-runner mcp`, which inherits the run, the token, the socket and the home from the CLI's environment and takes the run from `AGENTES_MCP_RUN`), or the bridge's URL with the token as a bearer in a file of the turn's own, removed with it. A turn without an account is refused (`not_logged_in`). Every `COPILOT_` variable of the runner's environment or the agent's secrets is kept out (`COPILOT_GITHUB_TOKEN`, another provider's `COPILOT_PROVIDER_*`, `COPILOT_ALLOW_ALL`), and so are `GH_TOKEN` and `GITHUB_TOKEN`, which the CLI would think as instead of the account; it gets only `COPILOT_QUIET_ENV`. The GitHub CLI's config (`GH_CONFIG_DIR`) is an empty folder of the account's for every Copilot process, a turn's and a look's alike, since the CLI thinks with `gh`'s sign-in when its own folder holds none; a Copilot agent's own `gh` commands therefore don't find the computer's `gh` sign-in in a file. `COPILOT_` is a reserved secret name; `GH_TOKEN` and `GITHUB_TOKEN` are not, and still reach agents on the other CLIs.
4. **Permission profiles** (ADR 0053 §3). `work`: `--allow-all-tools --allow-all-urls`, never `--allow-all-paths`, so its file tools stay in the turn's folder and the temp directory. `plan`: `--allow-tool read`, our MCP server, `--deny-tool write`; whatever else would ask is denied, and commands the CLI knows as read-only still run. The folder is never trusted, so a checkout's MCP servers, hooks and instructions stay out (ADR 0117). The CLI's own sandbox stays off: the agent's OS user is the boundary, as for OpenCode, and the shared folder (ADR 0115) isn't offered to a Copilot agent's prompt.
5. **Accounts** (ADR 0041, 0059): a device-code sign-in in a new folder (`copilot login --device-code`, GitHub's device page and its code, `parseCopilotLogin`). Status is a look (`copilotLook`, `copilot-acp.ts`): one run of the CLI's ACP server in the account's folder (`--acp --stdio --no-auto-update --disable-builtin-mcps --no-custom-instructions`) with `initialize` and `session/new` on standard input; models listed is signed in, "Authentication required" signed out, anything else unknown. The look's own session is removed from the folder by its id, and the folder is prepared as for a turn first, so nothing a turn left there loads in it. No sign-out command exists: removing the account removes the folder, where the sign-in is. One login per agent; never made for all agents where each is its own OS user (`sharesSignIns` false, as Grok's). No plan usage: the CLI shows it only in its terminal interface.
6. **Models.** "Quem pensa" offers `COPILOT_CLI_MODELS`, a hand-copied list; an id is taken as typed, since a plan's list changes often, and with none chosen the CLI's default runs. The runner reports no models: the CLI has no `models` command, and listing them takes a session of the computer's own sign-in, which no agent thinks with and whose folder (its MCP servers, plugins and history) a look every ten minutes has no business in. Copilot's own `auto` isn't offered: it is the engine's word for no model chosen. The runner refuses a model that isn't an id's characters (on Windows the CLI starts through cmd.exe).
7. **Apps.** Plan choice `copilot` (`PLAN_BRAIN`), GitHub Copilot's mark, the device code step on the web and the phone (the same steps as Grok's, on GitHub's page), its models in "Quem pensa", the tool switch in Ferramentas, every string in all fourteen languages. The desktop app adds no Copilot accounts yet, as with Grok's.
8. **Before it ships**, on a computer with a paid Copilot plan: that `copilot login --device-code` in an account's folder with our `settings.json` keeps the sign-in there (on Linux with and without a keyring, on macOS and on Windows) and a second account's folder stays signed out; that a turn in a signed-out account's folder fails rather than thinking with the computer's `gh` sign-in where that is kept in the OS credential store; a plan turn's denied edit and command; the words of a rate limit and of an exhausted plan; that `--reasoning-effort high` is taken by every model the list offers; a turn of an agent that is its own OS user (system mode).
9. **Install**: the core installs no coding CLI. Self-hosters install GitHub's (`npm install -g @github/copilot`, SELF_HOSTING.md); in system mode it must be where every agent's user can run it.

## Not done

- **The team's right hand on a Copilot plan** (ADR 0137 §4). The CLI's output names its tools nowhere before its first model call (no `init` line, as Claude Code's, Grok Build's and the Antigravity CLI's have), so a turn can't be checked to hold only our bridge before it thinks. The runner refuses a `chat` turn (`tools_not_locked`) and the apps don't offer the plan there. `--available-tools` with a guard on each `toolRequests` entry is the way in, once run.
- The computer's own Copilot sign-in (no account): it is whoever uses the computer's, often through `gh`.
- A plan's own model list in "Quem pensa": an account's look reads it, but the protocol has nowhere to carry an account's models yet. Copilot's `auto` routing.
- The CLI's command sandbox; live steering; plan usage (premium requests and AI credits are in `session.usage_checkpoint`, not yet read); Copilot accounts added from the desktop app; GitHub Enterprise Cloud with data residency (`--host`).

## Risks we accept

- No sandbox: in `work`, Copilot runs anything as the agent's user; its file tools stay in the turn's folder, its shell doesn't. `plan` holds only by the CLI's own permission checks. A turn's shell can write in the account's folder (`config.json` holds the sign-in and the trusted folders), which no later turn's cleanup can tell from the CLI's own writes.
- The JSONL events are not a documented contract: a CLI update can change them. The mapper ignores what it doesn't know, and a run that says and calls nothing fails rather than answering empty.
- Where the OS has a credential store and the computer's user is signed in to `gh`, a signed-out account may still read as signed in and think as that user (§8): the empty `GH_CONFIG_DIR` covers a sign-in kept in a file, not one in the store (seen on Windows 11).
- GitHub's terms for Copilot plans are the person's to accept: a plan is licensed per person, and "Atende outras pessoas" on a Copilot plan shows the same note as the other plans'.

## Consequences

- A GitHub Copilot plan thinks for its owner's agents on any computer whose runner is 65 or newer with the Copilot CLI installed. The turn isn't refused on Windows, as the other per-turn CLIs' are (the message goes on standard input and the CLI starts through the same quoting as Claude Code's).
- Everything Copilot-specific is behind runner protocol 65 and `kind: "copilot"`: older runners and servers never see it.
- Tests: a fake Copilot CLI (`apps/server/test/runner/fake-copilot.mjs`) for the runner's turns, sessions, usage, sign-in and looks, on every platform; the engine's brain, availability and options; the clients' plan choice and picker.

## Alternatives considered

- **The Agent Client Protocol for turns** (`copilot --acp`): finer control (a permission request per tool, model switches mid-session), at the cost of a second protocol in the runner beside every other CLI's one process per turn. Used only for the look, where nothing else answers.
- **A fine-grained token as the account** (`COPILOT_GITHUB_TOKEN`, sealed like an OpenCode key): the identity would be pinned whatever the computer holds, but the person would make a token by hand on GitHub's settings. The device code is the CLI's own sign-in and the same steps people know from ChatGPT and Grok.
- **The prompt as `-p <text>`**: an argument's limit would cut long contexts (as Cursor's and Grok's are) and the text would show in the process list.
