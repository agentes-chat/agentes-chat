# OpenID Connect single sign-on

Workspace owners can configure one standards-compliant OIDC identity provider in **Settings → Workspace → Single sign-on**. The same UI and API work on agentes.chat Cloud and self-hosted servers. Configuration is workspace-scoped; another workspace's owner cannot change it. Existing password and social login methods remain available by default.

1. Create a confidential web client at your identity provider using the authorization-code grant and PKCE (`S256`).
2. Turn on **Single sign-on** to expand its settings. Enter the issuer (or `/.well-known/openid-configuration` URL) and choose **Check provider** to confirm discovery and load its advertised scopes. Copy the client ID and secret from your provider’s web application, choose a display name, and save. A new connection only becomes active after its settings are saved.
3. Use the copy button beside the exact **Callback URL** shown after saving and register it at your identity provider. It has the form `https://YOUR-SERVER/api/auth/sso/callback/sso-PROVIDER-UUID`. Use this server callback for web, desktop and mobile alike; do not register a native app scheme at the provider.
4. Share the **Sign-in link**, `https://YOUR-SERVER/login?sso=sso-PROVIDER-UUID`.
5. Existing members first sign in with their existing method, then open **Settings → Your account → Single sign-on** and choose **Link SSO to your account**. Linking and configuration require a sign-in within the last ten minutes. Test the shared link in a separate browser after linking.

## Show SSO on the server login page

On a self-hosted server, set `AUTH_SSO_PROVIDER_ID` to the `sso-...` ID from the saved sign-in link and restart the server. The normal `/login` page then shows **Continue with your provider**, including in the desktop app, without entering an email or opening a special link. Only the explicitly selected provider is advertised; other workspace providers are not listed publicly.

After linking existing accounts and verifying a fresh SSO login, you may also set:

```dotenv
AUTH_SSO_PROVIDER_ID=sso-11111111-1111-4111-8111-111111111111
AUTH_SSO_ONLY=true
```

`AUTH_SSO_ONLY` defaults to `false` and requires the provider ID. It hides password/social forms and rejects their sign-in and password-reset endpoints on the server, including direct API calls. Invitations and SSO identity checks still apply. Existing sessions, stored passwords, conversations and identity links remain intact; a server restart does not sign everyone out. Native apps retain their verified browser handoffs. The selected provider cannot be disabled in workspace settings while this mode is on.

If the IdP becomes unavailable, set `AUTH_SSO_ONLY=false` in the server environment and restart to recover the existing password or social login. Keep server administration access available. Configure, link and test SSO before enabling this policy; do not enable it during first-owner setup.

The issuer is immutable after the connection is saved. A blank client-secret field on edits keeps the saved secret. The secret is encrypted with the installation's normal key wrapper (KMS where configured), never returned by the API, and travels with database backups. Self-hosted recovery needs the same `AGENTES_SECRET` and any configured key wrapper. Settings are read on each OIDC request, so changes need no restart and reach every replica. Configuration changes are recorded in the workspace audit log without secrets.

Discovery must return the configured issuer exactly, HTTPS authorization/token/JWKS endpoints, and an asymmetric ID-token signing algorithm. A trailing slash in an issuer is significant. `openid`, `profile` and `email` start selected and appear as compact chips with plain-language names and their scope values. Only `openid` is required by OpenID Connect and stays locked. Owners can remove and re-add `profile`, `email` or any extra scope; saved selections are used unchanged at sign-in apart from ensuring `openid` is present. The provider must still return a verified email, even if the `email` scope is removed. **Check provider** reads the optional `scopes_supported` metadata and offers unselected scopes in the **Add scope** picker, without selecting extras automatically. A provider may omit that list or some supported scopes, so **Add a custom scope** reveals a field for one scope at a time. Selected optional scopes appear as small removable buttons. Name and email remain available to add back even when discovery omits them. The picker rejects spaces and duplicates and keeps the existing 20-scope limit. See the [OpenID scope definitions](https://openid.net/specs/openid-connect-core-1_0.html#ScopeClaims) and [discovery metadata](https://openid.net/specs/openid-connect-discovery-1_0.html#ProviderMetadata). The provider must supply a stable `sub` and a verified email (`email_verified: true`), either in its signed ID token or matching UserInfo. Token endpoint authentication uses `client_secret_basic` when advertised, otherwise `client_secret_post`. Requests have a ten-second timeout; redirects are rejected. Cloud and servers open to public sign-up use the existing public-HTTPS network guard for discovery, token, UserInfo and key requests, including DNS rebinding protection. Closed self-hosted servers can use private HTTPS identity providers with trusted TLS certificates.

SSO authenticates an account; it never grants workspace membership or roles. New identities need a pending email invitation to the connection's own workspace, even when general sign-up is open. They still accept that invitation through the normal flow. An invitation for another workspace does not qualify. Existing accounts are never linked solely by matching email: explicit linking requires the same fresh live local session on return and the provider's verified email must match. Memberships, roles and the local account ID are preserved. The plugin keys identities by provider ID and subject, never email. Each provider ID belongs to one connection with an immutable issuer, preserving the issuer/subject boundary. Like linking another social login, linking SSO authorizes that provider to sign in to the whole local account; the linking UI states this explicitly.

OIDC runs through the official [`@better-auth/sso` plugin](https://better-auth.com/docs/plugins/sso), using the `ssoClient()` client plugin, `authClient.signIn.sso` and its `/sign-in/sso` and `/sso/callback/:providerId` endpoints. Better Auth owns discovery during sign-in, authorization-code exchange, state, PKCE, JWT/JWKS validation and account/session creation. The application resolver adds explicit linking, nonce and verified-email checks, and workspace invitation admission. Only those OIDC endpoints are exposed; provider administration stays behind the workspace-owner UI/API, with no automatic organization provisioning or email-based account linking. The plugin model maps to `oidc_providers`; its field transform opens the existing encrypted secret only on the server. The native auth transaction also covers the application admission checks. A small versioned plugin patch supplies the guarded HTTP transport and an OIDC nonce bound to Better Auth state; see [ADR 0171](adr/0171-ui-configured-oidc-sso.md) for its scope and upgrade checks. Web sessions remain HttpOnly cookies. Desktop sign-in keeps its confirmation-code handoff; mobile keeps its verifier-bound browser handoff and leaves no browser session. Sign-out ends the local session; it does not sign out of the identity provider. To recover from an IdP outage, use an existing password or another linked sign-in method. The owner must keep another sign-in method before disabling SSO. The Single sign-on toggle immediately saves changes for an existing connection. Turning it off disables SSO and collapses the form, preserving the configuration and identity links for re-enabling later. A failed change restores the toggle to its previous state.

Tests use a synthetic OIDC provider with real RSA-signed tokens and no external credentials. They cover both deployment types, account linking, invitations, rejected claims, and the native handoffs. Vendor-specific production IdPs and physical desktop/mobile apps still need operator validation.

The provider check is owner-only, rate limited, and uses the same HTTPS discovery validation and network guard as sign-in. It sends no client ID or secret and does not save configuration or authenticate a user. Provider availability and scope choices remain tied to the currently entered issuer, so a slow check of a previous URL cannot change the form.

Migration 0254 adds the plugin model fields without changing migration 0253. It backfills existing connections and converts earlier issuer/subject JSON account keys to the plugin’s subject key under the same immutable provider ID, preserving user IDs and memberships. The callback URL is now `/api/auth/sso/callback/sso-PROVIDER-UUID`; use the exact URL shown in settings.
