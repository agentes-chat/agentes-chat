# OpenID Connect single sign-on

Workspace owners can configure one standards-compliant OIDC identity provider in **Settings → Workspace → Single sign-on**. The same UI and API work on agentes.chat Cloud and self-hosted servers. Configuration is workspace-scoped; another workspace's owner cannot change it. Existing password and social login methods remain available.

1. Create a confidential web client at your identity provider using the authorization-code grant and PKCE (`S256`).
2. Turn on **Single sign-on** to expand its settings. Enter the issuer (or `/.well-known/openid-configuration` URL), client ID, client secret, display name and scopes, then save. A new connection only becomes active after its settings are saved.
3. Copy the exact **Callback URL** shown after saving and register it at your identity provider. It has the form `https://YOUR-SERVER/api/auth/callback/sso-PROVIDER-UUID`. Use this server callback for web, desktop and mobile alike; do not register a native app scheme at the provider.
4. Share the **Sign-in link**, `https://YOUR-SERVER/login?sso=sso-PROVIDER-UUID`.
5. Existing members first sign in with their existing method, then open **Settings → Your account → Single sign-on** and choose **Link SSO to your account**. Linking and configuration require a sign-in within the last ten minutes. Test the shared link in a separate browser after linking.

The issuer is immutable after the connection is saved. A blank client-secret field on edits keeps the saved secret. The secret is encrypted with the installation's normal key wrapper (KMS where configured), never returned by the API, and travels with database backups. Self-hosted recovery needs the same `AGENTES_SECRET` and any configured key wrapper. Settings are read on each OIDC request, so changes need no restart and reach every replica. Configuration changes are recorded in the workspace audit log without secrets.

Discovery must return the configured issuer exactly, HTTPS authorization/token/JWKS endpoints, and an asymmetric ID-token signing algorithm. A trailing slash in an issuer is significant. `openid`, `profile` and `email` are always requested; additional scopes can be entered separated by spaces. The provider must supply a stable `sub` and a verified email (`email_verified: true`), either in its signed ID token or matching UserInfo. Token endpoint authentication uses `client_secret_basic` when advertised, otherwise `client_secret_post`. Requests have a ten-second timeout; redirects are rejected. Cloud and servers open to public sign-up use the existing public-HTTPS network guard for discovery, token, UserInfo and key requests, including DNS rebinding protection. Closed self-hosted servers can use private HTTPS identity providers with trusted TLS certificates.

SSO authenticates an account; it never grants workspace membership or roles. New identities need a pending email invitation to the connection's own workspace, even when general sign-up is open. They still accept that invitation through the normal flow. An invitation for another workspace does not qualify. Existing accounts are never linked solely by matching email: explicit linking requires the same fresh live local session on return and the provider's verified email must match. Memberships, roles and the local account ID are preserved. Identity keys contain the issuer and subject, never the email address. Like linking another social login, linking SSO authorizes that provider to sign in to the whole local account; the linking UI states this explicitly.

OIDC uses the existing Better Auth authorization-code, state and PKCE flow, with server-bound provider selection, nonce verification, JWKS signature verification, issuer/audience/authorized-party checks and token expiry checks. Web sessions remain HttpOnly cookies. Desktop sign-in keeps its confirmation-code handoff; mobile keeps its verifier-bound browser handoff and leaves no browser session. Sign-out ends the local session; it does not sign out of the identity provider. To recover from an IdP outage, use an existing password or another linked sign-in method. The owner must keep another sign-in method before disabling SSO. The Single sign-on toggle immediately saves changes for an existing connection. Turning it off disables SSO and collapses the form, preserving the configuration and identity links for re-enabling later. A failed change restores the toggle to its previous state.

Tests use a synthetic OIDC provider with real RSA-signed tokens and no external credentials. They cover both deployment types, account linking, invitations, rejected claims, and the native handoffs. Vendor-specific production IdPs and physical desktop/mobile apps still need operator validation.
